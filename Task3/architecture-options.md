# Сравнение архитектурных вариантов для FinUnion + RetailBank

**Для целевого состояния через 12 месяцев предлагаю гибрид: централизованный DWH для сверенной отчётности, Data Lakehouse для исторических и событийных данных, а также доменное владение данными - без обязательного перехода на полноценный Data Mesh в первый год.**

При этом сравниваемые подходы находятся на разных уровнях. **DWH на PostgreSQL** — вариант реализации аналитического хранилища. **Data Lakehouse** - архитектура хранения и обработки данных. **Data Mesh** - подход к организации аналитических данных и ответственности команд, который может использовать и DWH, и Lakehouse. Его основные принципы - доменное владение, данные как продукт, платформа самообслуживания и федеративное управление.

Для нашего выбора определяющими являются ограничения проекта: отсутствие полной остановки клиентских сервисов, поэтапная миграция RetailBank, корректность финансовых данных, изоляция аналитической нагрузки, первый результат через три месяца и целевое состояние через год. 

## 1. Сравнение подходов

## 2. Выбранный целевой подход

### Централизованная гибридная платформа с доменной ответственностью

Предлагаемая архитектура объединяет три решения:

|Часть решения|Что выбираем|Граница ответственности|
|---|---|---|
|**Регламентированная аналитика**|Единый корпоративный DWH; PostgreSQL рассматриваем как вариант реализации после нагрузочной проверки|Согласованные данные, финансовые сверки, фиксированные отчётные срезы, сертифицированные витрины и показатели|
|**История и большие данные**|Lakehouse: объектное хранилище + Apache Iceberg + вычислительные движки по потребности|Исходная история, события, версии записей, повторная обработка и исследовательские наборы|
|**Управление данными**|Централизованные стандарты и общая платформа, владельцы данных в бизнес-доменах|Ответственность за смысл, качество и контракты данных без немедленной передачи всей разработки и эксплуатации доменным командам|

Такой выбор соответствует целевым требованиям задания: в них отдельно предусмотрены DWH для регламентированной отчётности, Lakehouse для больших исторических и событийных данных, каталог, управляемые пайплайны и правила владения.

### DWH: данные, на основании которых выпускается отчётность

В DWH предлагаю хранить **не только агрегаты, но и необходимую для отчётности проверенную детализацию и историю**.

Для твоих сущностей это, например, сверенные **Транзакции** и **Платёжные поручения**, состояния **Счетов** и **Договоров** на отчётную дату, версии **Графиков платежей**, значения **ПДН** и **ПСК**, связанные с конкретными условиями договора.

Витрины должны использовать единую идентификацию **Клиента**, согласованные **Кредитные продукты**, **Тарифы**, **Дополнительные услуги** и **Справочники**. Для **Обращений клиента** и **Согласий** формируются аналитические представления, но оперативная проверка согласия остаётся задачей авторитетного операционного реестра.

**Регламентированные отчёты и официальные показатели BI публикуются из этого проверенного слоя**, а не из необработанных событий.

### Lakehouse: исходная история и возможность повторной обработки

В Lakehouse предлагаю сохранять исходные изменения всех 14 сущностей, идентификаторы источников и историю загрузок. Это позволит повторно построить аналитические наборы при изменении правил сопоставления клиентов, исправлении ошибок преобразования или переносе портфелей RetailBank.

Особое внимание - истории **Транзакций**, состояний **Платёжных поручений**, условий **Договоров**, **Графиков платежей**, результатов расчётов **ПДН** и **ПСК**.

Для Iceberg необходимо отдельно определить политику хранения снимков: после их удаления соответствующее состояние уже нельзя использовать для time travel. Поэтому **снимки таблиц не следует считать автоматической заменой бизнес-истории и архивной политики**.

### Доменное владение: по бизнес-смыслу, а не по принадлежности к банку

Для начала предлагаю следующую группировку ответственности:

|Область ответственности|Твои бизнес-сущности|
|---|---|
|**Клиентские данные и обслуживание**|Клиент, Согласие, Обращение клиента|
|**Счета и платёжные операции**|Счёт, Транзакция, Платёжное поручение|
|**Кредитование и договорные условия**|Договор в части кредитования, График платежей, ПДН, ПСК|
|**Продуктовые и справочные данные**|Кредитный продукт, Тариф, Дополнительная услуга, Справочник|

Некредитные договоры остаются в ответственности соответствующего продуктового направления. Это **группировка владения**, а не требование создать четыре новые системы или четырнадцать отдельных продуктов данных.

FinUnion и RetailBank при этом не становятся двумя независимыми доменами данных: для каждой предметной области назначается общая ответственность, а различия банков сохраняются как происхождение данных и особенности обслуживаемых портфелей.

## 3. Почему гибрид предпочтительнее каждого подхода отдельно

### Только PostgreSQL DWH - недостаточно обоснованный выбор для всей платформы

PostgreSQL остаётся разумным кандидатом для структурированной отчётности. Однако размещать в нём одновременно все исходные события, полную историю обоих банков, исследовательские наборы и регламентированные витрины **без оценки нагрузки я бы не закладывал**.

Разделение позволяет не заставлять одну СУБД обслуживать все сценарии. При этом причина выбора Lakehouse - требования к истории и обработке, а не недоказанное утверждение, что PostgreSQL «не справится».

### Только Lakehouse - возможен, но увеличивает объём преобразований первого года

Регламентированный DWH-слой можно спроектировать и поверх Lakehouse. **Отдельная физическая СУБД для DWH не является обязательным свойством любой правильной архитектуры.**

Но для данного проекта предлагаю сохранить отдельный проверенный отчётный контур: это позволяет развивать историческую платформу, не связывая выпуск совместной отчётности с завершением всей её реализации. Если существующий FU DWH соответствует требованиям, его развитие предпочтительнее необоснованной замены ради выбранного стека.

### Полноценный Data Mesh - преждевременная организационная цель

В материалах подтверждены дубли клиентов, разные форматы, несинхронизированные справочники и раздельная отчётность. Значит, первоочередная проблема проекта - **согласование данных двух банков**.

## Итоговое решение

Для FinUnion + RetailBank выбирается централизованная гибридная архитектура: корпоративный DWH для проверенной регламентированной и управленческой отчётности, Data Lakehouse для исходной истории и событий, централизованный MDM и доменное владение данными. PostgreSQL рассматривается как реализация DWH при подтверждённой производительности и эксплуатационной пригодности. Полноценный Data Mesh не является обязательной целью первого года: его внедрение откладывается до появления подтверждённой потребности и готовности доменных команд.
