# 1. Архитектурная концепция
Для FinUnion Group построим единую логическую платформу данных с разделением операционного и аналитического контуров, сохранив на переходный период существующие банковские системы FinUnion и RetailBank.

Основной принцип: объединяем данные и правила управления ими, но не пытаемся за 12 месяцев физически объединить все банковские системы.

Это особенно важно с учётом ограничений задания: нельзя останавливать клиентские сервисы, одновременно заменять все системы RetailBank или допускать нарушение целостности финансовых данных.

### Целевые архитектурные решения

| Область                      | Решение To-Be                                                                                                                              |
| ---------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------ |
| Операционные системы         | Сохраняем FU Core, FU CRM, FU Cards, FU Loans как основу целевого ландшафта. RB-системы постепенно мигрируют или выводятся из эксплуатации |
| Мастер-данные                | Централизованный MDM для клиентов, продуктов и нормативно-справочной информации                                                            |
| Синхронная интеграция        | API Gateway + Integration Services для унифицированного доступа к данным                                                                   |
| Асинхронная интеграция       | Apache Kafka для доменных событий и CDC-потоков                                                                                            |
| Регламентированная аналитика | Единый корпоративный DWH с согласованными финансовыми показателями                                                                         |
| Большие данные               | Data Lakehouse для истории, событий, сырых данных и исследовательской аналитики                                                            |
| BI                           | Единый логический BI-слой с согласованными метриками                                                                                       |
| Оркестрация                  | Apache Airflow для batch ETL/ELT и проверок качества                                                                                       |
| Управление данными           | DataHub для каталога, lineage, владельцев и классификации данных                                                                           |
## 2. Принципы целевой архитектуры

1. Single Source of Truth по доменам. У каждой ключевой сущности определён авторитетный источник. При этом MDM не подменяет собой АБС или кредитную систему.
    
2. Единая идентификация клиента. Один глобальный `party_id` связывает клиентские записи FinUnion и RetailBank, сохраняя локальные идентификаторы.
    
3. Разделение OLTP и OLAP. Отчётность и аналитика работают с DWH и Lakehouse, а не выполняют тяжёлые запросы к банковским системам.
    
4. Событийная интеграция. Изменения передаются через CDC и доменные события, а синхронные API применяются для запросов и операций, которым необходим немедленный ответ.
    
5. Финансовая достоверность. Транзакции, проводки и остатки сохраняют связь с авторитетными банковскими источниками, проходят сверки и не изменяются при объединении клиентских профилей.
    
6. Проверяемое происхождение данных. DataHub связывает источники, трансформации, витрины, владельцев и потребителей.
    
7. Эволюционная миграция. Используем поэтапное переключение потребителей и продуктовых процессов вместо единовременного переноса всех систем.

### 4.1. Operational Systems

Не создаваем единую универсальную операционную БД для всех банковских сущностей.

Сохраняем предметные границы:

- CRM отвечает за обращения и клиентские взаимодействия.
    
- Core Banking отвечает за счета, остатки, проводки и учётные операции.
    
- Cards отвечает за жизненный цикл карт.
    
- Loans отвечает за кредитные договоры, задолженность и графики платежей.
    

В период миграции две АБС могут оставаться авторитетными источниками для разных портфелей счетов. Это допустимо при условии, что для каждого конкретного счёта однозначно известна его мастер-система.

### 4.2. MDM

MDM целесообразно разделяем логически на две области.

Customer/Party MDM формирует золотую запись клиента, присваивает глобальный идентификатор и хранит связи с исходными системами.
Пример:

```
party_id: P-00012345
  ├── FU CRM: C-10293
  ├── RB CRM: R-88372
  ├── FU Core: F-58124
  └── RB Core: B-44218

При этом MDM хранит историю слияния и разделения клиентских записей, источники атрибутов и правила разрешения конфликтов.

Reference Data MDM обеспечивает единые справочники продуктов, тарифов, клиентских сегментов, отделений и кодов статусов. Для действующих договоров необходимо сохранять исторические версии тарифов и условий, а не автоматически заменять их актуальными значениями.

### 4.3. Integration Layer и Kafka

Интеграционный слой разделяется на два механизма:

#### Синхронный REST API
Применяется для получения актуального состояния счёта, проверки доступности продукта, выполнения операций и получения единого клиентского профиля.

#### Асинхронные события и CDC
Применяются для распространения изменений клиентов, продуктов, счетов, кредитов и операций, а также для загрузки данных в аналитическую платформу.


Для Kafka предусматриваются Schema Registry, версионирование контрактов, контроль consumer lag, DLQ для некорректных сообщений и идемпотентная обработка.

CDC фиксирует изменения источников, но сам по себе не заменяет бизнес-события. Например, изменение строки кредитного договора и событие `LoanIssued` имеют разную семантику.

### 4.4. DWH и Data Lakehouse

Я бы не делал DWH и Lakehouse двумя независимыми хранилищами, в которых дублируется вся информация.

Разделение аналитических нагрузок

| Enterprise DWH                                                                                                                                    | Data Lakehouse                                                                                                                                                                                         |
| ------------------------------------------------------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| Регламентированные, сверенные и согласованные данные.<br><br>Финансовая и регуляторная отчётность, управленческие KPI, сертифицированные витрины. | Исторические, событийные, сырые и крупнообъёмные данные.<br><br>CDC-история, события, архивы, подготовка датасетов для риск-аналитики.<br><br>Контролируемые загрузки и повторное использование данных |

Предпочтительная модель: Lakehouse хранит исходные и подготовленные наборы, а DWH - проверенные данные и регламентированные витрины. При этом критичные финансовые данные могут поступать в DWH напрямую из контролируемых источников, если этого требуют сроки отчётности и процедуры сверки.

Для Lakehouse можно рассмотреть объектное хранилище с Apache Iceberg и вычислительными движками Spark/Trino. Для DWH - развитие FU DWH либо новую платформу после оценки текущих возможностей. Конкретные СУБД заданием не определены.

## 6. Основные потоки данных

Поток 1. Объединение клиентов

FU CRM / RB CRM → Integration Layer → Customer MDM → глобальный `party_id` → Kafka → CRM, DWH, Lakehouse.

Результат: единая идентификация и связанный клиентский профиль.

Поток 2. Финансовые операции

FU/RB Core → CDC → Kafka → Lakehouse / DWH → сверки → финансовые витрины → BI.

Результат: консолидированная отчётность без прямой аналитической нагрузки на АБС.

Поток 3. Продукты, карты и кредиты

FU/RB Cards, Loans → CDC / события → Kafka → нормализация по общей модели → DWH / Lakehouse.

Результат: единое аналитическое представление портфеля и продуктовых показателей.

Поток 4. Регламентированная отчётность

Airflow → контролируемые загрузки → Data Quality → сверки DWH с источниками → сертифицированные витрины → BI / отчётные системы.

Результат: воспроизводимая отчётность с фиксированными отчётными срезами.

Отдельно для клиентских каналов необходим Customer 360 API. Он собирает профиль из MDM и актуальные сведения о продуктах из авторитетных операционных систем. DWH не должен использоваться как основной источник для критичных операций в реальном времени.

## 7. Управление качеством, безопасностью и происхождением данных

|Механизм|Целевое решение|
|---|---|
|Data Quality|Проверки полноты, уникальности, корректности связей, согласованности кодов и финансовых сумм|
|Lineage|DataHub отслеживает путь от источника через Kafka и ETL/ELT до витрины BI|
|Data Ownership|Data Office управляет стандартами; бизнес-владельцы отвечают за определения и качество доменных данных|
|Безопасность|RBAC/ABAC, шифрование, маскирование ПДн, аудит доступа|
|Историчность|Версионирование мастер-данных, сохранение исходных идентификаторов, история изменений|
|Финансовые сверки|Контроль количества операций, оборотов, остатков и расхождений между источниками и DWH|
|Надёжность|Повторная обработка, идемпотентность, контроль задержек CDC и восстановления пайплайнов|
