## 2. Пайплайн промежуточного состояния — PostgreSQL DWH (3 месяца)

Цель: обеспечить единую управленческую отчётность FinUnion и RetailBank без полной миграции существующих систем.

Упрощённая схема временного аналитического контура

Логика обработки:

1. Airflow запускает регулярные пакетные загрузки из доступных источников, предпочтительно через реплики или существующие DWH.
    
2. Данные загружаются в staging-слой PostgreSQL с сохранением исходных идентификаторов.
    
3. Выполняются нормализация форматов, сопоставление клиентов по единому идентификатору и контроль качества.
    
4. dbt формирует согласованные модели клиентов, счетов, продуктов и операций.
    
5. BI использует готовые витрины для единой управленческой отчётности.
    

Особенности: PostgreSQL DWH используется как временное решение. Операционные системы продолжают работать независимо, а аналитическая нагрузка не должна влиять на клиентские операции.

Важное ограничение: единый клиентский идентификатор на этом этапе можно реализовать через таблицу соответствия идентификаторов FU/RB без ожидания полноценного внедрения MDM.

## 3. Сценарии обработки больших данных

### Сценарий 1. Консолидация истории карточных операций

|Поле|Описание|
|---|---|
|Источник данных|FU Cards, RB Cards, архивные выгрузки карточных процессингов|
|Характер данных|Исторические, транзакционные, архивные|
|Целевое хранилище|Data Lakehouse (объектное хранилище + Apache Iceberg)|
|Способ обработки|Batch для исторической загрузки, CDC для последующих изменений, Spark для преобразования|
|Потребители|BI, риск-менеджмент, антифрод, регуляторная отчётность|

Обработка: исторические данные обоих банков загружаются пакетами в объектное хранилище. Spark выполняет унификацию форматов операций, сопоставление идентификаторов карт и клиентов, дедупликацию и контроль полноты данных. Результаты сохраняются в таблицах Iceberg.

Последующие изменения поступают через CDC при наличии технической поддержки. Для регламентированной отчётности необходимые агрегаты и сверенные данные передаются в DWH.

Особое внимание уделяется сохранению оригинальных финансовых записей, обработке сторнирований и исключению повторного учёта операций.

### Сценарий 2. Обработка событий клиентских каналов

|Поле|Описание|
|---|---|
|Источник данных|Мобильные приложения, веб-приложения FinUnion и RetailBank|
|Характер данных|Событийные, полуструктурированные (JSON)|
|Целевое хранилище|Data Lakehouse|
|Способ обработки|Streaming через Kafka, Spark Structured Streaming|
|Потребители|BI, антифрод, риск-менеджмент, клиентская аналитика|

Обработка: клиентские каналы публикуют события авторизации, действий пользователя, оформления продуктов и выполнения операций в Kafka.

Spark Structured Streaming обрабатывает события, проверяет структуру, устраняет дубликаты по идентификаторам событий и сохраняет данные в Lakehouse. При необходимости формируются агрегаты клиентской активности для аналитических витрин.

Это позволяет анализировать поведение клиентов и выявлять аномалии без прямой аналитической нагрузки на операционные системы.

## 4. Архитектурные принципы реализации

|Принцип|Реализация|
|---|---|
|Разделение OLTP и OLAP|Аналитика выполняется в DWH и Lakehouse, а не в операционных БД|
|Единый клиент|MDM управляет мастер-данными и связями идентификаторов FU/RB|
|Сохранение финансовой корректности|Контрольные суммы, сверка количества и сумм операций, идемпотентная загрузка|
|Качество данных|Проверки полноты, уникальности, форматов и ссылочной целостности|
|Трассируемость|Фиксация источника, времени загрузки, версии преобразования и lineage|
|Защита данных|Шифрование, разграничение доступа, маскирование персональных данных|
|Поэтапная миграция|Сосуществование legacy-систем и целевой платформы до завершения миграции|
