## 2. Общие механизмы надёжности

Для всех критичных потоков предлагаются единые механизмы:

1. Идемпотентность. Повторная доставка сообщения не должна приводить к повторному созданию клиента, платежа или транзакции.
    
2. Контроль порядка. Изменения одной сущности обрабатываются с учётом версии и последовательности событий.
    
3. Schema Registry. Контракты данных версионируются, несовместимые изменения не допускаются без согласования.
    
4. Retry и DLQ. Временные ошибки обрабатываются повторно, некорректные сообщения направляются в карантин для разбора.
    
5. Мониторинг. Контролируются задержка доставки, ошибки, отставание потребителей, полнота данных и успешность сверок.
    
6. Безопасность. Применяются шифрование, разграничение доступа, маскирование персональных данных и аудит операций.
    
7. Lineage. Для данных фиксируется путь от мастер-системы через интеграционные компоненты до аналитической витрины.
    

## 3. Контроль качества данных

|Уровень|Проверки|Действие при нарушении|
|---|---|---|
|Ingress|Формат, схема, обязательные поля, дубли доставки|Отклонение или карантин записи|
|Domain|Бизнес-правила, статусы, коды, связи между сущностями|Регистрация DQ-инцидента|
|Reconciliation|Количество записей, денежные суммы, остатки, контрольные итоги|Повторная сверка, блокировка некорректной публикации|
|Publication|Полнота витрины, актуальность, согласованность метрик|Запрет публикации критически некорректных данных|

## 4. Управление потоками на этапах миграции

| Этап                           | Приоритетные потоки                                 | Результат                                                                                        |
| ------------------------------ | --------------------------------------------------- | ------------------------------------------------------------------------------------------------ |
| MVP - 3 месяца                 | F01–F07, F11–F12, F14–F18, F20 в необходимом объёме | Единый идентификатор клиента, базовая синхронизация, консолидированная управленческая отчётность |
| Целевое состояние - 12 месяцев | Все F01–F22                                         | Полноценные MDM, DWH, Data Lakehouse, каталог данных, контроль качества и управляемые интеграции |

В MVP не обязательно реализовывать все потоки в полном объёме: приоритет определяется минимальным набором данных для единой отчётности и клиентского профиля.

Важный архитектурный принцип: MDM отвечает за мастер-данные и идентификацию, операционные системы остаются источниками финансовых операций, а DWH отвечает за консолидацию и отчётность. Нельзя превращать MDM или DWH в промежуточный транзитный сервис для выполнения банковских операций.

При миграции историческая загрузка F20 должна согласовываться с инкрементальными потоками CDC: через snapshot и watermark необходимо обеспечить отсутствие пропусков и двойного учёта.
