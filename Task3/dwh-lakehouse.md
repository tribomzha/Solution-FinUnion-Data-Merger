# Сравнение DWH на PostgreSQL и Data Lakehouse для FinUnion + RetailBank

Для нашей архитектуры выбираем **гибрид: DWH для проверенных отчётных данных и Data Lakehouse для исходной истории, событий и повторной обработки**. MDM и операционные системы остаются мастер-системами бизнес-сущностей.

Такое разделение соответствует целевому состоянию задания: отдельно предусмотрены DWH для регламентированной отчётности, Lakehouse для исторических и событийных данных, каталог и управляемые пайплайны. о-задании

**PostgreSQL рассматриваем как кандидат на реализацию DWH**, а не как уже подтверждённую замену существующего FU DWH. Окончательный выбор зависит от нагрузочных испытаний и оценки действующей платформы.

## 1. DWH на PostgreSQL

| Параметр                       | Описание применительно к нашему варианту                                                                                                                                                                                                                                                                         |
| ------------------------------ | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| **Назначение**                 | Консолидированная управленческая и регламентированная отчётность двух банков: проверенные финансовые данные, согласованные показатели, отчётные срезы и BI-витрины.                                                                                                                                              |
| **Хранение**                   | Реляционные таблицы и индексы. **Стандартное хранение PostgreSQL - строчное, а не колоночное.** В нашем DWH предусматриваем загрузочный слой, согласованную детальную модель и отчётные витрины.                                                                                                                 |
| **Производительность**         | Рассматриваем для SQL-запросов, соединений таблиц и формирования витрин. Материализованные представления позволяют заранее сохранять результаты расчётов; параллельное выполнение может ускорять часть запросов. Однако скорость тяжёлых агрегаций и одновременной работы BI необходимо подтвердить испытаниями. |
| **Загрузка данных**            | Предусматриваем первоначальные пакетные загрузки и последующее применение изменений. PostgreSQL поддерживает массовую загрузку через `COPY`, поэтому большие загрузки не следует заранее считать его принципиально слабой стороной.                                                                              |
| **Изменение структуры**        | PostgreSQL поддерживает изменение таблиц через `ALTER TABLE`. В проекте изменения модели сопровождаем миграциями и  совместимости витрин, загрузок и отчётов.                                                                                                                                                    |
| **Согласованность**            | Транзакции позволяют атомарно выполнять связанные изменения внутри БД. Для финансовой достоверности дополнительно проектируем сверки с источниками, контроль полноты загрузок и фиксацию отчётного периода. Наличие транзакций само по себе не проверяет правильность отчётных показателей.                      |
| **Стоимость**                  | В расчёт включаем данные, индексы, журнал изменений, резервирование, резервные копии и вычислительные ресурсы. Не закладываем обязательное использование только SSD и не выводим стоимость из одного количества записей.                                                                                         |
| **Поддержка**                  | Для SQL-преобразований рассматриваем `dbt-postgres`, для пакетной оркестрации - Airflow. Эти инструменты дополняют PostgreSQL, но не заменяют проектирование загрузок и контроля качества.                                                                                                                       |
| **Ограничения и применимость** | Для FinUnion используем прежде всего как проверенный отчётный контур. Всю исходную событийную историю помещать сюда не планируем. Допустимые объёмы и конкурентную нагрузку определяем испытаниями, а не условным порогом «данные старше двух лет».                                                              |

**В DWH храним не только агрегаты.** Для проверки отчётов предусматриваем необходимую детализацию: транзакции, платёжные поручения, состояния счетов и договоров, версии графиков платежей и связанные расчётные показатели.

## 2. Data Lakehouse: Iceberg + Trino

| Параметр                       | Описание применительно к нашему варианту                                                                                                                                                                                                                                                |
| ------------------------------ | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| **Назначение**                 | Сохранение исходных данных FinUnion и RetailBank, событий, изменений записей и бизнес-истории. Основа для повторных расчётов, восстановления аналитических наборов и исследовательской аналитики.                                                                                       |
| **Хранение**                   | Для проекта выбираем файлы **Parquet в S3-совместимом объектном хранилище**, таблицы Apache Iceberg и отдельный каталог таблиц. Iceberg управляет схемами, составом файлов, разбиением данных и снимками состояния.                                                                     |
| **Производительность**         | Trino выполняет распределённые SQL-запросы на нескольких узлах. Используем его для обработки больших исторических наборов и аналитических выборок. Не предполагаем, что любая операция будет быстрее или «почти такой же быстрой», как в PostgreSQL: это проверяется на наших запросах. |
| **Гибкость структуры**         | Iceberg поддерживает эволюцию схемы и разбиения таблиц; поддерживаемые изменения могут выполняться через метаданные без переписывания существующих файлов. Но изменение бизнес-смысла атрибутов по-прежнему требует согласования контрактов и корректировки преобразований.             |
| **Согласованность**            | Iceberg обеспечивает атомарные изменения и чтение согласованного снимка таблицы. **Lakehouse не лишён транзакционных гарантий**, однако на этом основании нельзя считать автоматически согласованными весь набор таблиц и внешний PostgreSQL DWH.                                       |
| **Стоимость**                  | Объектное хранилище рассматриваем как способ экономичнее размещать длительную историю. Экономию проверяем по полной стоимости: хранение, вычисления Trino, обслуживание таблиц, резервирование, сеть и эксплуатация. Утверждение «в разы дешевле» без расчёта не используем.            |
| **Поддержка**                  | Для SQL-преобразований через Trino рассматриваем **`dbt-trino`**, а не абстрактный «Iceberg-adapter». Пакетные задания и зависимости организуем в Airflow.                                                                                                                              |
| **Ограничения и применимость** | Потребуется обслуживание таблиц: объединение мелких файлов, управление снимками и очистка неиспользуемых файлов. Для нашего кейса Lakehouse выбираем как исторический и событийный контур, не подменяющий операционные системы.                                                         |


## 3. Выбранный подход и этапы внедрения

| Период                                 | Выбор                                                           | Обоснование и содержание                                                                                                                                                                                                                                                                                                                                                                                                          |
| -------------------------------------- | --------------------------------------------------------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| **Промежуточное состояние - 3 месяца** | **Единый отчётный контур + начало накопления исходной истории** | Формируем первые совместные витрины по клиентам, счетам, договорам и операциям. Используем единый клиентский идентификатор и согласованные соответствия FU/RB. Для приоритетных источников запускаем Kafka и сохранение изменений в исходную зону объектного хранилища. Существующие DWH используем как контролируемые источники там, где подтверждены происхождение и правила расчёта данных, а не просто объединяем их таблицы. |
| **Целевое состояние - 12 месяцев**     | **Постоянная гибридная архитектура: DWH + Data Lakehouse**      | В DWH находятся сверенные детальные данные, отчётные срезы и сертифицированные витрины. В Lakehouse - исходная история, события и подготовленные наборы для согласованного периметра всех 14 бизнес-сущностей. Airflow управляет пакетными обработками; DataHub связывает наборы с определениями, владельцами и происхождением.                                                                                                   |
| **Решение о физической платформе DWH** | **PostgreSQL - после подтверждения пригодности**                | Проверяем одновременные загрузки, BI-запросы, закрытие периода и пересчёт истории. Если существующий FU DWH удовлетворяет требованиям, его не заменяем исключительно ради PostgreSQL.                                                                                                                                                                                                                                             |


## 4. Роль Iceberg, Trino и объектного хранилища

| Компонент                              | Роль в нашей архитектуре                                                                                                                                                                                                          |
| -------------------------------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| **S3-совместимое объектное хранилище** | Физическое размещение файлов данных и метаданных Lakehouse. Само по себе не является SQL-движком или системой управления бизнес-сущностями.                                                                                       |
| **Apache Iceberg**                     | Табличный формат: схемы, снимки, история состояния таблиц, атомарная публикация изменений и организация файлов для чтения. Не отдельная СУБД и не самостоятельный вычислительный движок.                                          |
| **Каталог таблиц Iceberg**             | Регистрация таблиц и доступ к их актуальным метаданным. Выбираем отдельную совместимую реализацию, например REST-каталог. **Hive Metastore - вариант каталога метаданных, а не кэш запросов.**                                    |
| **Trino**                              | Распределённый SQL-движок для Lakehouse. Через отдельные коннекторы может обращаться к Iceberg и PostgreSQL, в том числе для запросов к разным источникам. Для нашего проекта такой доступ ограничиваем аналитическими системами. |


## 5. Распределение наших 14 бизнес-сущностей

Ниже предлагаемое распределение данных. **Наличие сущности в DWH или Lakehouse означает аналитическое представление, а не перенос мастерства.**

| Бизнес-сущности                                                 | Мастер-система                                                                      | PostgreSQL DWH                                                                            | Data Lakehouse                                                            |
| --------------------------------------------------------------- | ----------------------------------------------------------------------------------- | ----------------------------------------------------------------------------------------- | ------------------------------------------------------------------------- |
| **Клиент**                                                      | Customer MDM; CRM и Core предоставляют исходные данные                              | Согласованное представление клиента, необходимая история атрибутов и связи с продуктами   | Исходные профили FU/RB, история изменений и сопоставлений идентификаторов |
| **Счёт, Договор**                                               | Core или Loans в зависимости от сущности и типа договора                            | Проверенные состояния на отчётную дату, условия, остатки и связи с клиентом               | История исходных изменений, версий условий и статусов                     |
| **Транзакция, Платёжное поручение**                             | Core; процессинг - источник связанных карточных событий                             | Детальные сверенные операции, статусы исполнения, суммы и отчётные агрегаты               | Исходные события, изменения статусов и история обработки                  |
| **График платежей, ПДН, ПСК**                                   | Loans в принятой проектной модели                                                   | Версии и значения, используемые в отчётности, с привязкой к договору и дате расчёта       | История графиков, расчётов, изменений условий и версий методик            |
| **Кредитный продукт, Тариф, Дополнительная услуга, Справочник** | Product / Reference MDM; индивидуальные условия и подключения - продуктовая система | Согласованные справочные измерения и версии, применимые к конкретным договорам и периодам | История опубликованных версий, исходных кодов и соответствий FU/RB        |
| **Обращение клиента, Согласие**                                 | CRM / авторитетный реестр согласий                                                  | Показатели обслуживания и аналитические срезы по согласиям                                | История обращений, получения и отзыва согласий                            |


## 6. Ограничения выбранного подхода и меры управления

| Ограничение                                         | Как учитываем в нашей архитектуре                                                                                                                                                                                                                                                                                                                      |
| --------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| **Две платформы усложняют эксплуатацию**            | Назначаем владельцев компонентов и пайплайнов, вводим мониторинг загрузок, задержек и ошибок. Airflow используем для пакетной оркестрации; непрерывную обработку Kafka не возлагаем на него.                                                                                                                                                           |
| **Повторное хранение и расхождение показателей**    | Утверждаем единые определения показателей и версии преобразований. В DWH сохраняем необходимую детализацию и витрины, в Lakehouse — исходную и подготовленную историю. Не реализуем независимые формулы одного показателя в разных контурах.                                                                                                           |
| **Повторы и нарушения порядка при загрузке**        | Предусматриваем идемпотентное применение изменений, идентификатор источника, ключ записи, версию и контроль позиции обработки. **Транзакционный producer Kafka сам по себе не гарантирует exactly-once во внешних хранилищах** — необходима согласованная работа коннектора и приёмника. Outbox применяем там, где можем изменить приложение-источник. |
| **Несогласованность отчётных срезов**               | Фиксируем границы загрузки, отчётный период и версии преобразований. Проверяем полноту, суммы и связи сущностей. Не публикуем официальный отчёт до завершения обязательных сверок.                                                                                                                                                                     |
| **Смешение ролей каталогов и реестров**             | Разделяем обязанности: Schema Registry — контракты событий; каталог Iceberg — технические метаданные таблиц; DataHub — определения, владельцы и lineage. DataHub получает схемы из источников и реестров, а не становится автоматически единым реестром всех контрактов.                                                                               |
| **Рост числа файлов и снимков Lakehouse**           | Планируем объединение мелких файлов, обслуживание метаданных и очистку по утверждённым срокам. Правила очистки не должны уничтожать историю, необходимую для воспроизведения отчётности.                                                                                                                                                               |
| **Доступ к персональным и финансовым данным**       | Вводим раздельные права на исходные данные и витрины, маскирование, шифрование и аудит. Классификацию фиксируем в каталоге, а права обеспечиваем в PostgreSQL, Trino и объектном хранилище; для Trino возможна интеграция с Ranger.                                                                                                                    |
| **Неподтверждённая производительность и стоимость** | До окончательного выбора конфигураций измеряем объёмы, прирост, конкурентность и сроки обработки. Проверяем нагрузку при одновременной загрузке, работе BI и пересчёте истории. Не назначаем произвольные SLA и объёмы хранения.                                                                                                                       |
