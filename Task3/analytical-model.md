# Аналитическая модель FinUnion — анализ финансовых операций

## 1. Выбор аналитической области и модели

Для FinUnion Group выбрана аналитическая область «Финансовые операции клиентов» с использованием схемы «звезда» (Star Schema).

Модель предназначена для формирования единой управленческой отчётности по операциям клиентов FinUnion и RetailBank после объединения банков.

Она позволяет анализировать:

- Объёмы и количество финансовых операций.
    
- Активность клиентов по сегментам.
    
- Распределение операций по продуктам, счетам и каналам обслуживания.
    
- Динамику операций по датам и регионам.
    
- Финансовые показатели отдельно по FinUnion и RetailBank и в консолидированном виде.
    

Выбор этой области обусловлен требованиями задания: объединить отчётность двух банков, обеспечить единый клиентский идентификатор и отделить аналитическую нагрузку от операционных систем.

## 3. Grain - детализация факта

Одна строка `fact_transaction` соответствует одной проведённой финансовой операции (учётной строке) из конкретной системы-источника.

Один платёж может формировать несколько фактов: основную операцию, комиссию, возврат или корректировку.

Для объединения данных используется составной бизнес-идентификатор:

`source_system + source_transaction_id + posting_line_no`

Это предотвращает конфликты идентификаторов между FinUnion и RetailBank.

## 4. Состав аналитической модели

|Тип таблицы|Таблица|Основные атрибуты|Назначение|
|---|---|---|---|
|Fact|`fact_transaction`|transaction_key, customer_key, account_key, product_key, date_key, amount, fee_amount, transaction_count|Проведённые финансовые операции|
|Dimension SCD2|`dim_customer`|customer_key, global_customer_id, segment, customer_type|Анализ по единому клиенту и сегменту|
|Dimension SCD2|`dim_account`|account_key, account_id, account_type, status|Анализ операций по счетам|
|Dimension SCD2|`dim_product`|product_key, product_id, product_type, tariff|Анализ по банковским продуктам|
|Dimension|`dim_date`|date_key, date, month, quarter, year|Анализ динамики операций|
|Dimension|`dim_channel`|channel_key, channel_name, channel_type|Мобильное приложение, веб, офис|
|Dimension SCD2|`dim_branch`|branch_key, branch_id, region|Анализ по отделениям и регионам|
|Dimension|`dim_currency`|currency_key, currency_code, currency_name|Анализ операций по валютам|
|Dimension|`dim_source_system`|source_key, source_name, bank_name|Разделение данных FinUnion и RetailBank|


## 5. Меры и показатели

| Мера                   | Описание                             | Агрегация                                       |
| ---------------------- | ------------------------------------ | ----------------------------------------------- |
| `transaction_amount`   | Сумма операции в исходной валюте     | SUM в рамках валюты и единой знаковой конвенции |
| `amount_base_currency` | Сумма в единой валюте отчётности     | SUM                                             |
| `fee_amount`           | Комиссия по операции                 | SUM                                             |
| `transaction_count`    | Значение 1 для каждой учётной строки | SUM                                             |
| `unique_customers`     | Количество уникальных клиентов       | COUNT DISTINCT по global_customer_id            |

## 6. Почему «звезда» подходит для OLAP

| Критерий           | Обоснование                                                                      |
| ------------------ | -------------------------------------------------------------------------------- |
| Производительность | Меньше JOIN по сравнению со «снежинкой», так как измерения денормализованы       |
| Агрегация          | Удобный расчёт SUM, COUNT, AVG и группировок по измерениям                       |
| Историчность       | SCD2 позволяет анализировать операции с учётом исторического состояния сущностей |
| Консолидация       | Единые измерения объединяют операции FinUnion и RetailBank                       |
| BI-инструменты     | Простая структура для построения аналитических витрин и дашбордов                |
| Масштабируемость   | Возможность партиционирования фактов по дате и применения колоночного хранения   |
| Изоляция нагрузки  | Аналитические запросы выполняются в DWH без обращения к OLTP-системам            |
|                    |                                                                                  |

## 7. Качество данных и историчность

Для корректной работы аналитической модели предусматриваются следующие правила:

- Дедупликация: уникальность сочетания `source_system + source_transaction_id + posting_line_no`.
    
- Единый клиент: сопоставление локальных идентификаторов с `global_customer_id` через MDM.
    
- Согласованность: проверка суммы и количества операций между DWH и источниками по дате и валюте.
    
- Историчность: привязка факта к актуальной на дату операции версии SCD2-измерения.
    
- Поздние данные: отдельная процедура загрузки и корректировки закрытых периодов.
    
- Lineage: сохранение системы-источника, идентификатора исходной записи и времени загрузки.
    
- Безопасность: исключение из аналитических фактов полных реквизитов карт, документов и других избыточных персональных данных.
    

## 8. Итог

Для аналитической области финансовых операций FinUnion выбрана схема «звезда» с центральной таблицей `fact_transaction` и девятью измерениями.

Модель позволяет построить единую отчётность FinUnion и RetailBank, анализировать финансовую активность по клиентам, счетам, продуктам и каналам, сохраняя историчность данных.

Она соответствует целевой архитектуре, в которой MDM отвечает за унификацию идентификаторов, DWH — за аналитические данные, а BI — за их представление.

При этом модель является логическим проектным решением: конкретные атрибуты, правила пересчёта валют, состав проводок и допустимые задержки загрузки необходимо согласовать с владельцами данных и финансовым департаментом.
